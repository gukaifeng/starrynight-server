# 语音逐次耗时追踪 · 服务端

## 目的与入口

控制室 `https://39.105.116.74:8444` → AI → **语音耗时**。每次对话、重播、语音识别和后台预生成单独留存，可按追踪 ID、角色和场景搜索，展开全部音频分段，导出完整 JSON。客户端开发者页面有对应的本地记录与服务端快照。

这里记录实际执行的耗时，不补造旧会话的历史指标，不把音频长度算作生成延迟。本轮使用 `frontend-design` 的设计流程延续星夜控制室的雾色、月白和潮色，核心是能直接看出并行关系的时间轴。

## 关联与测量

- 客户端发出 `X-Starry-Voice-Trace` UUID；Go 网关校验格式并转发，不信任客户端伪造的网关指标。网关只从已验证会话派生账户身份。
- Go 分别计时会话鉴权、角色目录/可见权限、账户目标上下文，覆盖客户端→网关→AI worker 的业务前置环节。
- Worker 在纯 ASGI 入口记录起点；HTTP 校验、流生产启动、对话处理、逐段音频处理的时刻均相对此单调时钟。
- SSE 的业务事件添加 `trace_id`、`server_at_ms`；结束追加 `voice.trace` 快照。旧客户端可忽略新增字段/事件。快照不包含凭证、对话正文、提示词、声音标识或 PCM。
- 客户端与服务端用追踪 ID 关联，**不相减两台设备的墙钟时间**。客户端 URLSession 网络阶段是客户端自己的观测值；服务端 span 是服务端自己的观测值。

## 环节清单

| 层 | 记录内容 |
|---|---|
| 网关 | 鉴权、角色权限、目标上下文；伪造网关指标被删除 |
| Worker | 入站校验、生产任务启动、上下文加载 |
| 预生成 | 缓存检查、命中/未命中、已就绪/仍生成、优先级队列、后台让出资源、接管时文字和音频的等待 |
| 对话模型 | 用量登记、模型与尝试序号、HTTP 请求、JSON 解码、结构校验、语言和去重审查 |
| 模型网络 | 使用现有 HTTPcore 官方 trace 扩展：传输分派、TCP/DNS、TLS、发送请求头/体、等待响应头、接收响应体、关闭响应；不保存 callback 的 info 字典 |
| 表演 | 并行模型调用、动作/表情解析，与语音生成独立的起止时间 |
| 持久化 | 保存对话与关系；语音缓存检查、读取、写入和整理 |
| 逐段 TTS | beat ID、模型、用量账本 ID、供应商请求 ID、响应头时刻、首 PCM 时刻、事件解码、PCM 解码、生成总时长、实际字节数及音频长度 |
| 有序交付 | 每次分段队列等待、音频 Base64 编码、SSE JSON 编码、向有界事件队列交付的等待 |
| ASR | 连接识别模型、启动任务、逐块上传、首个麦克风数据、首个识别结果、用户结束输入与识别完成 |

每个后台 draft 使用自己的追踪 ID，即 draft ID；前台命中记录携带 `preparation_trace_id`，可搜索它查看早先的生成成本。正在生成的 draft 被前台接管时，另记录前台实际等待。智能接话预测本身也有 `prepare:suggestions` 记录，每个候选回答有独立生成记录，不把三个候选的并行耗时相加。

## 如何定位慢

1. 先看手机的“到首次输出”，确定用户真正等待了多久。
2. 如果文字就很晚，检查网关、上下文、`model.plan.http`、质量审查/重试，以及 `conversation.register_opening` 的客户端等待。
3. 如果文字快但音频晚，检查 TTS 响应头/首 PCM、音色是否就绪、预缓存是否命中，或 `preparation.inflight_audio_wait`。
4. 如果服务器首音频已快，手机仍晚，检查 URLSession 网络阶段、客户端事件队列、音频会话、引擎启动、PCM 转换和首次缓冲提交。
5. 第二段之后断续，检查有序队列等待、网络分块间隔和客户端 `audio.drain`。播放等待往往只是正常音频长度，应与生成/排队区分。
6. 确认是否后台页面、静音、取消或失败；没有输出的记录不伪造为零延迟。

TCP 计时可能包含 TLS；下载、TTS 生成和各并行任务可能重叠。模型内部的排队/推理时间没有供应商独立指标，归入等待响应。流中快照截至生产完成，不代表网关最后一个字节发送完成或手机播放完成。

## 存储与兼容

AI worker 现有私有 SQLite WAL 增加 `voice_traces` 表，`(owner,id)` 为复合主键、`owner/character/created` 和 `created` 有索引；避免另一账户用相同 trace ID 覆盖记录。保留最近 14 天且最多 5000 次；每次最多 1024 个 span，超限明确记录 `dropped_spans`。记录纳入现有完整备份。只通过已鉴权的管理平台读取，不新增公开日志下载接口。

耗时写入不进入计费账本，也不参与对话记忆。取消/异常会留存已完成的测量；不因此重试已可能计费的模型请求。并发任务通过 ContextVar 隔离，后台任务建立自己的作用域，不把后续预生成混进已结束的前台请求。

## 验证与问题处理

- Python 全套及专项测试覆盖并发隔离、取消留存、私有信息不写入、相同 ID 的账户隔离、真实等待计时。
- Go vet/race/build 与真实 PG/Redis 集成覆盖原有鉴权及可信 header 边界；TypeScript/Vite/Vitest 验证管理平台。
- Chrome 检查时间轴、全部环节切换、JSON 导出，桌面与 390×844 手机布局；离线样例明确标为 `verification:timeline`，不作为真实模型速度结论。
- 客户端模拟器使用真实 AVAudioEngine 和测试 PCM 验证播放、转换、缓存和 drain；不调用付费模型。
- 本机隔离管理员密码与云端不同，使用各自私有密码文件；未修改线上管理员或用户密码。
- 本轮不调用图片模型，也不通过付费对话来制造性能样本。上线后的实际慢请求会自然留下可比较的记录。
