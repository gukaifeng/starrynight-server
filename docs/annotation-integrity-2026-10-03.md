# 回复括号与非发音描写修复

用户报告的案例中，「扶着额头，故作痛苦」进入了台词字符串。原动作识别没有覆盖这两个短语，因此没有拒绝该字符串；分句器又在括号内的逗号处分段，插入另一个表情描写，最终把同一对括号拆到不同 UI 片段，造成孤立右括号及误朗读。按该样例可以确定这条代码路径，但未声称读取了该次真实用户的请求或音频。

本次处理：

- 动作识别补充扶额、揉额、捂脸、故作、转头等中英文动作及少量明确心声模式；新台词禁止混入这些描写或不配对的括号，沿用既有内部 schema 校正流程。语气、心理与实际表演仍通过结构字段传递。
- 分句器保护完整括号区域。自然停顿、语气词和锚点不能把括号或其中的文字拆成两个台词片段；普通「维生素（B12）」「明天（如果有空）再聊」保留。
- 旧回复的 TTS 输入修复孤立闭括号后的动作续文；兼容换行、没有换行、嵌套及中英宽度混用的括号。没有明确动作语义的普通文字保留，不凭空补写角色台词。
- 有问题的旧台词用独立音频修复键；正常缓存 key 不变，避免让已缓存正常语音全部失效。角色预生成、音频播放、管理员文件关联及删除对话后的音频清理使用一致规则。
- `reply_flow.REVISION` 升为 5，旧结构的待触发候选不再被新场景直接领取；正常问候、接话与动作预缓存仍沿既有逻辑后台补齐。

## 无付费验证

用户给出的格式、换行与原文逐字成为 `test_annotation_integrity.py` 的回归输入。验证朗读输入不含扶额、故作痛苦、表情或心声，正常说话部分保留；同时检查新规划拒绝错误台词、括号内不插入心声、普通括号台词保留、仅异常音频改键。测试不调用模型或语音供应商。

完整 Python 测试：284 passed、4 skipped。Go race 单元测试与构建通过。最初直接运行集成测试缺少环境变量；加载本机测试配置后，旧 `starry_test` 数据库有历史迁移版本与 sequence 不一致问题。本次没有改动该数据库或迁移源码，使用独立的新建 `starry_annotation_test` 数据库执行现有 PostgreSQL/Redis 集成测试，全部通过。临时本机开发服务测试结束后已停止，不改变云端权威入口。

客户端同步修复旧片段括号状态及语音缓存选择；真实 PCM 缓存播放、渐进文字显示和结构化翻译另在客户端项目验证。没有重新生成角色图、音色或预置音频，不把文本输入测试声称为厂商付费 TTS 的实测。
