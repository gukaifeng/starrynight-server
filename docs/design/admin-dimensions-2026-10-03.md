# 控制台：用户、角色、后台数据三个维度

## 目的与仓库边界

这次修改只发生在独立服务端仓库，不改客户端、不重新打包客户端资源、不调用图片生成或付费对话接口。用户授权验证后直接部署到现有 HTTPS 8444 管理入口。实现基于当前 Gin 管理进程、React / Headless UI / Tailwind 前端、PostgreSQL 和独立 Python AI 服务；没有新增另一套鉴权、SQL 编辑器或服务器执行入口。

开发使用独立 `admin-dimensions` 工作目录，基于 `7182e70` 同步了另一位开发者刚提交的原始角色名称和问候资源更新，保留其内容。部署前再次确认活动版本与源码一致。

## 三种主要入口

| 维度 | 目录 | 详情与操作 |
|---|---|---|
| 用户 | 星夜号、用户名、昵称、完整 UUID 搜索；注册／游客筛选；10 / 25 / 50 条分页 | 头像、资料、账号、星夜号、内部 UUID、设置、作者资料、订阅、作者关注、创作角色、会话、偏好、目标与羁绊、聊天归档、记忆、同步及反馈；AI 上下文、自动记忆、用量、耗时与预缓存按账户精确筛选 |
| 角色 | 包含公开、私人、未列出、下架角色；名称和 ID 搜索；游标分页 | 封面、头像、名称、作者、创建用户、元数据、资源发布、AI 设定／能力；订阅者、会话用户、聊天统计；从用户进入角色、从订阅者／聊天用户返回账户 |
| 后台数据 | 按对话、AI、内容、账户、运营、数据库／同步、管理分组的目录 | 保留原有全部已注册数据表、语音耗时、AI 请求、模型／提示词配置、预缓存与用量、管理员与审计；保留服务器服务、配置、文件、资源／对象存储、缓存、备份／恢复、版本与证书、维护任务的管理入口 |

用户和角色详情里的“全部数据”复用现有记录查看／编辑界面，查询改为当前对象的精确范围。用户与角色的组合还可进一步查看一段关系的完整归档与 AI 数据。资料编辑、版本冲突检测、重置、会话撤销等继续走已有的确认、权限与审计接口。范围页不提供未预填所属用户的“新建”按钮；全局后台数据仍保留原有创建入口。

关系页将目标模式、初始关系、长期方向、本次目标及已有的羁绊指标转成可读字段，并保留完整目标和所有分支 JSON。没有数据时展示“尚未保存”，不补造关系或进度。

## 数据口径与真实关联

- PostgreSQL `messages` 是客户端同步的账户归档。Python `messages` 是模型实际使用的上下文。两者分开标识、分开计数，绝不相加。
- 用户／角色头部显示账户归档统计，其下单独显示 AI 上下文、自动记忆、请求及场景预缓存；更多 AI 统计包含用量分组。单位账本不是人民币账单。
- PostgreSQL 关系查询是订阅、会话、偏好、目标的限定范围 UNION，避免只有偏好或订阅的角色被漏掉；可分别查看订阅与会话。
- AI 关系查询还包含只有请求、自动记忆、状态或预缓存的组合。历史 owner 保留原标识。即使格式像 UUID，也必须在 PostgreSQL 查到确切账户才显示账户跳转，不靠外形猜测关联。
- AI 列表采用 `owner = ?`、`character = ?` 的精确筛选；模糊搜索只能在该范围内缩小结果。角色设定按角色 ID 查询；全局提示词和预算不能误归入某个用户。
- 嵌入索引按原始消息的所属范围关联，只返回索引元数据，始终排除向量。凭据及音色私有标识继续由既有递归脱敏机制隐藏。

## 分页与数据库压力

新目录 API 统一位于 `/admin-api/v1/directory/`：`users`、`users/:id`、`characters`、`characters/:id`、`relationships`、`ai-relationships`、`records/:resource`。

1. 用户目录默认 25 条，允许 1–50 条；角色目录相同。查询取 `limit + 1` 判断后续页面，没有总数 COUNT，也没有大 OFFSET。详情按需加载；登录或进入用户目录不再自动请求全库总览。
2. 用户用真实 UUID 主键、角色用真实 ID、关系用用户／角色组合键、消息按 `sequence DESC` 翻页。其他限定范围的数据用原生复合主键。游标绑定资源、范围和搜索条件，校验长度、键数、UUID 与数字类型；切换搜索必须重新从第一页开始。
3. 用户和角色目录的三字以上搜索使用专用 trigram 索引；一、二字采用有 B-tree 索引的前缀搜索，避免过短 contains 条件退化成整库扫描。完整 UUID 搜索直接用主键，通配符按普通文字转义。
4. 新目录数据库请求有 5 秒上下文上限。超时显示缩小查询范围提示。聊天 JSON 搜索仍是当前对象内的搜索，不对全库资料 JSON 做目录检索。
5. Goose 00014 增加角色方向索引、目录搜索索引和 `admin_conversation_stats`。消息插入、删除、角色变更在同一 PostgreSQL 事务维护每个用户／角色的计数；不把每个角色的所有写请求集中到一个全局计数行。重复同步／文字编辑不增加条数；回滚不改变条数；会话级联删除同时清除统计。
6. 初次迁移在消息写锁内回填与安装触发器，防止回填期间漏算。这是一次性迁移；线上当前归档为空，回填量很小。大规模部署应安排迁移窗口，不能将写锁描述为完全无影响。
7. AI 服务为所有可按 owner / character 筛选的表补充幂等索引，关联页最多 25 个组合。仅在详情读取当前对象的汇总。没有后台轮询或自动全库抓取。

分页遵循 PostgreSQL 对唯一排序与大 OFFSET 成本的说明：[LIMIT/OFFSET 官方文档](https://www.postgresql.org/docs/current/queries-limit.html)。模糊查询使用已有 PostgreSQL pg_trgm 扩展：[索引支持官方文档](https://www.postgresql.org/docs/current/pgtrgm.html)。本次验证了功能正确性及小规模并发，没有宣称未知规模的吞吐上限。

## 权限与兼容

所有新接口继承独立管理 session、会话撤销和只读／编辑／所有者角色。App 登录态不能用于管理入口；匿名目录返回 401。写操作保持 Origin + CSRF 检查及既有审计。没有向浏览器发送内部 AI 管理 token；AI owner 关联由 Go 网关转发和补全账户信息。

客户端 `/v1` 公开契约、角色资源、语音生成管线和用户认证实现不变。数据库新增的统计表是管理用派生数据，客户端无需感知。原有数据表编辑入口仍可从后台数据访问。前端 hash 保存当前入口，刷新和浏览器返回能恢复到相应详情。

## 验证与遇到的问题

- 本机原有测试 PG / Redis 未运行。未恢复旧 Mac 服务，而是在此工作目录单独启动 57037 / 57038 的隔离测试实例，测试数据库与浏览器样例数据库分开。测试结束后停止。
- Go 真实 PostgreSQL／Redis 集成测试验证目录分页不重漏、范围隔离、私人角色、订阅与会话关联、全部支持资源、参数／游标校验、统计增删改／回滚／幂等与 12 路同时插入。沿用原有管理员权限、CSRF、审计、双实例 session 和头像安全测试。
- Go 转发 AI 的 UUID 数组最初使用 `[]uuid.UUID`，pgx 编码失败；已改为经过校验的 UUID 字符串数组，真实 PG 测试通过。未知 UUID 和 legacy owner 不会误链接到现存用户。
- AI 管理测试验证精确范围、转义搜索、worker-only 会话、分页边界、汇总、嵌入元数据不泄露向量和索引使用；没有付费调用。
- React / TypeScript 生产构建和现有前端单元测试通过。真实 Chrome 验收 1512×1050 与 390×844：三维度导航、分页／搜索、账户—角色往返、关系记录、AI 设定编辑界面、语音耗时入口、hash 刷新、窄屏无横向溢出。验收工具默认只读，线上不创建测试账户。
- 完整 Python 回归为 276 passed / 6 skipped / 1 failed。唯一失败为既有 `test_core_prompt_does_not_contain_the_large_avatar_catalogue` 对提示词少于 10000 字符的断言；在未包含本次控制台修改的 `7182e70` 主目录单独运行也失败（10065 字符）。本次不改他人的对话提示词、不调高阈值来掩盖问题。新增管理测试通过；部署记录保留这一已知基线问题。
- 原有 3D 资源预览分包仍有 Vite 大于 500 KB 的提示，预览模块保持按需加载，不在用户目录自动加载模型。
