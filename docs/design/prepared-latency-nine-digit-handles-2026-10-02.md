# 缓存交付与九位公开号码

## 这次确认的问题

快捷接话的三个回复分支原先串行等待完整文字、语音和表现输出。第二、第三个选项可见时，对应答案可能根本尚未开始准备。现在依可能性顺序启动三个任务，交给已有四槽优先队列控制并发，每项仍只准备一组；实际选中在途任务继续使用原任务，不重复请求。

前台命中候选后原先仍进入 `yield_to_reply`，取消所有其他准备任务并等待其清理完成。这会让缓存交付等待无关 provider/TTS 的退出，也毁掉其他事件尚未完成的储备。命中或接管已存在任务现在直接交付；普通未命中请求仍清理旧准备，选中接话后的未选择分支仍由 discard 取消和删除。

生产只读汇总确认既有命中也有 miss/inflight，准备失败包含 STRUCTURE_INVALID 与 DRAFT_AUDIO_FAILED。不是每条“有缓存”的场景都真的拥有完成的 PCM。客户端同步修复失败即停止补准备以及已结束任务句柄未释放的问题：最多三分钟、间隔匹配 worker 的 30 秒退避；只为缺项再次准备，不重新生成已就绪项。没有承诺冷启动、缓存过期、上下文变化或服务失败同样瞬时完成。

## 星夜号

新增 Goose 12，公开号码为 `xy` 加 `100000000 + 注册序号`，第一个分配序号对应 `xy100000001`。继续使用同一 PostgreSQL 注册序列，多 API 节点共享权威写库，不重新设定序列、不按用户数量计算、不复用注销或回滚空号。UUID 所有权不变，旧长号和短号均保留为退役别名。号码当前不可用户修改，将来改号仍须专用保留别名事务。
